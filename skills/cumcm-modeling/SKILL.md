# CUMCM 建模

把已确认的解题路线转成可审查、可实现、可验证的建模件。不要替 hub 改题意、跳过路线确认，或编造尚未运行的数值结果。

## 前置输入

开始前读取：

1. 当前任务契约，核对 `task_id`、`subquestion`、`role=modeler`、输入、输出和验收条款；
2. `plan.md` 中的 startup lock、路线确认记录和本任务依赖；
3. 题面与必要附件；有数据时读取 `data_profile.md`；
4. [建模检查清单](references/modeling-checklist.md)。

所有输入与输出路径必须是竞赛工作区相对路径。依赖未冻结、题意或单位不明、路线尚未确认时，按 hub 的 stop-and-report 格式返回 `blocked`，不得自行补全。

## 建模步骤

### 1. 固定问题边界

- 用一句话重述本子问题的决策对象、目标、已知量和交付物。
- 列出与其他子问题的输入输出关系，防止在局部模型里改写任务 DAG。
- 区分题面事实、数据观察、建模假设和待验证猜想。

### 2. 建立假设与符号

- 假设使用稳定编号 `A-P<i>-<n>`，逐条说明依据、适用范围、失效影响和验证方式。
- 符号表至少包含符号、含义、类型/维度、单位、取值域和来源。
- 同一概念全程使用同一符号；量纲不一致的表达式不得进入候选模型。
- 无法从题面或数据得到的参数标记为“待估计”，不得填入虚构数值。

### 3. 完成机制与公式

- 先给机制链，再写目标函数、约束、状态转移或评价关系。
- 每个关键公式说明变量来源、边界条件、单位和适用条件。
- 对评价、优化、预测、机理或综合题型执行检查清单中的对应防错项。
- 给出至少一个基线或替代路线，并说明最终路线在精度、可解释性、数据要求和算力上的权衡。
- 创新点必须说明相对基线实际增加了什么；标准方法不得包装成创新。

### 4. 设计验证

- 为每个主模型给出可判定的正确性或合理性检查。
- 预留关键参数灵敏度实验，并说明扰动范围依据与“结论稳定”的判据。
- 需要时加入基线对比、交叉验证、留出验证、极端边界、消融或稳健性检查。
- 明确模型不应被信任的条件，避免只列泛化的“模型缺点”。

### 5. 形成编程接口

建模件必须让 coder 无需猜测即可实现：

- 输入文件、字段、单位、缺失处理和允许的派生数据；
- 参数、默认值来源、随机过程和随机种子要求；
- 算法步骤或伪代码、终止条件、复杂度风险和失败路径；
- 预期结果文件的列名、单位、精度、场景口径和约束回代规则；
- 车道 A 图需求及每张图要证明的结论；
- 待核实的经典方法出处只写“引用需求”，不凭记忆生成参考文献。

## 必须产出

写入契约指定的 `reports/analysis_modeling_P<i>.md`，至少包含：

1. 问题边界与依赖；
2. 假设表和符号表；
3. 模型机制、公式与算法；
4. 候选路线权衡及最终选择；
5. 验证、灵敏度与稳健性方案；
6. 编程接口；
7. 引用需求、局限和未解决项。

不得在建模件中声称任何未由运行结果支持的量化结论。

## 反馈契约

完成后按 `Task feedback` 格式逐条对照 `acceptance`：

- `verdict` 只能是 `ready_for_review` 或 `blocked`；
- 列出实际输出、假设编号、待登记证据和执行过的检查；
- `ready_for_review` 只表示可送独立评审，不表示产物已冻结；
- 不得自批通过或直接把下游任务改为 `ready`。
